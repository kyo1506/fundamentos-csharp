# 02.4: Composição vs Herança: Favoring Composition over Inheritance

> **Fase 02: Programação Orientada a Objetos + SOLID** · Aula 4
> Objetivo: compreender os perigos do acoplamento excessivo por herança, aplicar o princípio "favoreça composição em vez de herança" e utilizar delegação e strategies para construir sistemas flexíveis.

---

## 1. O Problema da Herança Profunda

Herança é o acoplamento mais forte que existe na orientação a objetos. Uma classe filha passa a depender intimamente dos detalhes internos da classe mãe (problema conhecido como **fragilidade da classe base**).

### Sintomas de Herança Abusiva:
1. **Hierarquias profundas:** `Entidade` -> `EntidadeAuditoria` -> `Usuario` -> `UsuarioAdmin` -> `SuperAdminEspecial`.
2. **Explosão combinatória de subclasses:** `CarroGasolina`, `CarroEletrico`, `CarroGasolinaAutonomo`, `CarroEletricoAutonomo`...
3. **Herança forçada:** herdar de uma classe apenas para reaproveitar 1 método, trazendo consigo 10 outros métodos que não fazem sentido para o novo tipo (violação do princípio de substituição de Liskov).

---

## 2. O Princípio: Favoreça Composição

> *"Favor object composition over class inheritance."* (Design Patterns, Gang of Four)

Em vez de perguntar **"O que esse objeto É?"** (herança: "um Carro é um Veículo"), pergunte **"O que esse objeto TEM ou FAZ?"** (composição: "um Carro tem um Motor e um Sistema de Navegação").

```
  HERANÇA RÍGIDA                         COMPOSIÇÃO FLEXÍVEL
┌──────────────────────┐               ┌─────────────────────────────────┐
│ CarroEletrico        │               │ Carro                           │
│ (tudo engessado)     │               │ - IMotor _motor                 │
└──────────────────────┘               │ - INavegacao _navegacao         │
                                       └─────────────────────────────────┘
                                                       │
                                        ┌──────────────┴──────────────┐
                                        ▼                             ▼
                                  MotorEletrico                 NavegacaoGps
```

## 3. Exemplo Prático: Log e Notificação

### Abordagem Ruim com Herança
```csharp
public class RepositorioBase
{
    protected void Log(string msg) => Console.WriteLine($"[LOG]: {msg}");
}

// Para ter log, o serviço precisa herdar de RepositorioBase?
// Isso mistura persistência com regras de negócio e acopla desnecessariamente.
public class PedidoServico : RepositorioBase
{
    public void Processar()
    {
        Log("Processando...");
    }
}
```

### Abordagem Elegante com Composição
```csharp
public interface ILogger
{
    void LogInfo(string mensagem);
}

public class ConsoleLogger : ILogger
{
    public void LogInfo(string mensagem) => Console.WriteLine($"[INFO]: {mensagem}");
}

public class PedidoServico(ILogger logger)
{
    public void Processar()
    {
        logger.LogInfo("Processando pedido com composição desacoplada.");
    }
}
```

## 4. O Padrão Strategy: Flexibilidade Dinâmica

A composição permite inclusive **trocar de comportamento em tempo de execução**, algo impossível com herança pura:

```csharp
public interface ICalculoFrete
{
    decimal Calcular(decimal pesoKg);
}

public class FreteExpresso : ICalculoFrete
{
    public decimal Calcular(decimal pesoKg) => pesoKg * 15.0m + 20m;
}

public class FreteEconomico : ICalculoFrete
{
    public decimal Calcular(decimal pesoKg) => pesoKg * 5.0m;
}

public class CarrinhoDeCompras(ICalculoFrete calculoFrete)
{
    private ICalculoFrete _calculoFrete = calculoFrete;

    public void AlterarModalidadeFrete(ICalculoFrete novoCalculo)
    {
        _calculoFrete = novoCalculo ?? throw new ArgumentNullException(nameof(novoCalculo));
    }

    public decimal ObterCustoFrete(decimal pesoTotal) => _calculoFrete.Calcular(pesoTotal);
}
```

## 5. Diretrizes para Decisão
- Use **herança** quando:
  - Existir uma relação "é um" autêntica e invariável.
  - A subclasse puder ser usada em **qualquer** lugar onde a classe base é esperada sem surpresas ou exceções.
  - A hierarquia for rasa (geralmente não mais que 1 ou 2 níveis).
- Use **composição** quando:
  - O comportamento puder variar ou for compartilhado entre famílias de classes não relacionadas.
  - Você quiser testar a classe isoladamente injetando fakes/mocks.
  - Você precisar alterar o comportamento em tempo de execução.
