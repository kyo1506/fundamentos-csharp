> Objetivo: consolidar o design de contratos enxutos, entender o padrão de Injeção de Dependência (DI) por construtor sem mágica de frameworks e preparar o terreno para arquiteturas profissionais testáveis.

## 1. O que é Injeção de Dependência (DI)?

Injeção de Dependência é uma técnica para alcançar a **Inversão de Controle (IoC)**. Em vez de uma classe criar suas próprias dependências (usando `new Servico()`), as dependências são fornecidas ("injetadas") a partir de quem instancia a classe, tipicamente via parâmetro no construtor.

```
SEM INJEÇÃO (Acoplamento forte):
[ServicoDeMatricula] ──new──> [SqlServerMatriculaRepository] ──new──> [SmtpEmailSender]

COM INJEÇÃO (Desacoplamento total via contratos):
[ServicoDeMatricula] ──depende de──> [IMatriculaRepository] & [INotificador]
         ▲
      injetado por quem orquestra (Main ou DI Container)
```

---

## 2. Injeção por Construtor com Primary Constructors (C# 12+)

O C# moderno torna a injeção de dependência por construtor extremamente concisa e limpa através de **Primary Constructors**:

```csharp
public interface IAlunoRepositorio
{
    Aluno? ObterPorDocumento(string cpf);
    void Salvar(Aluno aluno);
}

public interface INotificadorMatricula
{
    void NotificarSucesso(string email, string curso);
}

// Injeção limpa e direta na declaração da classe:
public class ServicoMatricula(
    IAlunoRepositorio repositorio,
    INotificadorMatricula notificador)
{
    public bool Matricular(Aluno aluno, string curso)
    {
        ArgumentNullException.ThrowIfNull(aluno);

        var existente = repositorio.ObterPorDocumento(aluno.Documento);
        if (existente is not null)
            return false; // Já matriculado

        repositorio.Salvar(aluno);
        notificador.NotificarSucesso(aluno.Email, curso);
        return true;
    }
}
```

## 3. Por que isso Transforma a Testabilidade?

Com injeção de dependência, você pode testar a lógica de negócio de `ServicoMatricula` **sem precisar de um banco de dados real ou de um servidor de e-mail**, usando implementações em memória (Fakes/Mocks):

```csharp
public class AlunoRepositorioFake : IAlunoRepositorio
{
    private readonly Dictionary<string, Aluno> _alunos = new();

    public Aluno? ObterPorDocumento(string cpf) =>
        _alunos.GetValueOrDefault(cpf);

    public void Salvar(Aluno aluno) =>
        _alunos[aluno.Documento] = aluno;
}

public class NotificadorSpy : INotificadorMatricula
{
    public int TotalNotificacoesEnviadas { get; private set; }

    public void NotificarSucesso(string email, string curso)
    {
        TotalNotificacoesEnviadas++;
    }
}

// No teste unitário:
var repoFake = new AlunoRepositorioFake();
var notificadorSpy = new NotificadorSpy();
var servico = new ServicoMatricula(repoFake, notificadorSpy);

var aluno = new Aluno("12345678901", "Lucas", "lucas@teste.com");
var sucesso = servico.Matricular(aluno, "C# Avançado");

Assert.True(sucesso);
Assert.Equal(1, notificadorSpy.TotalNotificacoesEnviadas);
```

## 4. O "Composition Root" (Raiz de Composição)

A raiz de composição é o ponto único de entrada do aplicativo (normalmente o método `Main` ou o bootstrap em `Program.cs`) onde as instâncias concretas são criadas e conectadas:

```csharp
public static class Program
{
    public static void Main()
    {
        // Raiz de composição manual (sem containers complexos):
        IAlunoRepositorio repo = new AlunoRepositorioEmMemoria();
        INotificadorMatricula notificador = new NotificadorConsole();

        var servico = new ServicoMatricula(repo, notificador);

        servico.Matricular(new Aluno("99999999999", "Julia", "julia@dev.io"), "Arquitetura .NET");
    }
}
```

## 5. Resumo da Fase 02
Ao concluir esta fase, você domina:
1. **Encapsulamento:** proteger invariantes com campos privados e propriedades validadas.
2. **Herança consciente:** usar `virtual`/`override` e classes abstratas com moderação.
3. **Polimorfismo e Interfaces:** desacoplar o que deve ser feito de como é feito.
4. **Composição sobre Herança:** construir tipos modulares e flexíveis.
5. **SOLID:** projetar código manutenível, extensível e robusto.
6. **Injeção de Dependência:** código desacoplado e 100% testável.
