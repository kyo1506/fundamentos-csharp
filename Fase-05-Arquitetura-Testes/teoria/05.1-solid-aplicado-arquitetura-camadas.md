# Lição 05.1: SOLID Aplicado e Arquitetura em Camadas

Projetar software de qualidade exige ir além da sintaxe da linguagem. Uma arquitetura bem desenhada isola as regras de negócio de detalhes voláteis como frameworks de interface, bancos de dados e bibliotecas externas.

---

## 1. Revisão dos Princípios SOLID na Arquitetura

Na Fase 02 estudamos SOLID em nível de classes. Aqui, elevamos esses princípios para o nível arquitetural:

1. **Single Responsibility (SRP):** Cada camada ou pacote possui uma única razão para mudar. Se as regras de negócio de matrículas mudarem, apenas a camada de Domínio é alterada. Se o banco migrar de SQL Server para PostgreSQL, apenas a Infraestrutura é modificada.
2. **Open/Closed (OCP):** A arquitetura deve permitir adicionar novas funcionalidades ou canais de entrega sem reescrever o núcleo existente.
3. **Liskov Substitution (LSP):** Contratos de repositórios e serviços de domínio devem ser substituíveis por implementações em memória, relacionais ou NoSQL sem quebrar os casos de uso.
4. **Interface Segregation (ISP):** Interfaces enxutas e focadas. A camada de aplicação não deve depender de interfaces inchadas de infraestrutura.
5. **Dependency Inversion (DIP):** O princípio fundamental da arquitetura moderna: módulos de alto nível (regras de negócio) não dependem de módulos de baixo nível (acesso a dados, IO, APIs externas). Ambos dependem de abstrações (interfaces).

---

## 2. A Regra de Dependência e Clean Architecture

Nas arquiteturas limpas (Clean Architecture, Ports and Adapters, Onion Architecture), o sistema é organizado em camadas concêntricas:

```
[ Apresentação / CLI / Web ]  (Camada Externa)
             │
             ▼
[ Aplicação / Casos de Uso ]
             │
             ▼
[ Domínio / Entidades / Regras ]  (Núcleo Central - Zero dependências externas)
             ▲
             │
[ Infraestrutura / EF / IO ]   (Implementa contratos do Domínio)
```

### A Regra de Ouro
**As setas de dependência de código-fonte sempre apontam para dentro, em direção ao Domínio.**
- O **Domínio** não referencia nenhum outro projeto, pacote ORM ou biblioteca externa. Ele contém apenas entidades puras, objetos de valor (`Value Objects`), exceções de domínio e interfaces de repositórios/serviços.
- A **Aplicação** orquestra os casos de uso utilizando os contratos definidos pelo Domínio.
- A **Infraestrutura** implementa os contratos do Domínio (ex: repositórios com Entity Framework Core ou Dapper, envio de e-mails via SendGrid).
- A **Apresentação** (Console, Web API, Blazor) configura a injeção de dependência e inicia o fluxo de execução.

## 3. Estrutura de Código Recomendada no .NET

Um projeto corporativo típico organiza seus assemblies da seguinte forma:

```
MeuSistema.slnx
├── src/
│   ├── MeuSistema.Domain/           # Entidades, Enums, Contratos de Repositório
│   ├── MeuSistema.Application/      # DTOs, Casos de Uso, Serviços de Aplicação
│   ├── MeuSistema.Infrastructure/   # Implementações de Repositórios, DB Context
│   └── MeuSistema.Presentation/     # Controllers, Minimal APIs ou Console
└── tests/
    ├── MeuSistema.Domain.Tests/     # Testes de unidade puros (rápidos)
    ├── MeuSistema.Application.Tests/# Testes de casos de uso com fakes
    └── MeuSistema.Integration.Tests/# Testes de banco e integração real
```

## 4. Inversão de Controle na Prática

Considere a regra: quando uma matrícula é concluída, um e-mail de confirmação deve ser enviado.

### Abordagem Acoplada (Ruim)
```csharp
public class MatriculaService
{
    public void Concluir(Matricula m)
    {
        m.Aprovar();
        // Erro: acoplado diretamente a um serviço externo concreto de envio de e-mails
        var emailSender = new SmtpEmailSender();
        emailSender.Enviar(m.AlunoEmail, "Aprovado!");
    }
}
```

### Abordagem com DIP e Arquitetura Limpa (Boa)
No projeto `Domain`:
```csharp
public interface INotificadorAluno
{
    Task NotificarConclusaoAsync(string email, string curso, CancellationToken ct = default);
}
```

No projeto `Application`:
```csharp
public class ConcluirMatriculaUseCase(
    IMatriculaRepository repository,
    INotificadorAluno notificador)
{
    public async Task ExecutarAsync(int matriculaId, CancellationToken ct = default)
    {
        var matricula = await repository.ObterPorIdAsync(matriculaId, ct)
            ?? throw new InvalidOperationException("Matrícula não encontrada.");

        matricula.Aprovar();

        await repository.AtualizarAsync(matricula, ct);
        await notificador.NotificarConclusaoAsync(matricula.AlunoEmail, matricula.CursoNome, ct);
    }
}
```

No projeto `Infrastructure`:
```csharp
public class SmtpNotificadorAluno : INotificadorAluno
{
    public async Task NotificarConclusaoAsync(string email, string curso, CancellationToken ct)
    {
        // Detalhe de baixo nível de envio de e-mail usando rede
    }
}
```

Dessa forma:
1. O caso de uso pode ser testado em milissegundos substituindo `INotificadorAluno` por um fake em memória.
2. Trocar de provedor de e-mail ou adicionar SMS exige zero alterações na lógica de negócio central.
