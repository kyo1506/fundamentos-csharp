# Lição 05.4: Testes Unitários com xUnit e Prática de TDD

Testes automatizados são a rede de proteção que permite refatorar e evoluir o código com segurança. Nesta lição, estudamos o framework **xUnit** e a metodologia **Test-Driven Development (TDD)**.

---

## 1. O Ciclo do TDD (Red, Green, Refactor)

No TDD, nenhum código de produção é escrito antes de existir um teste automatizado que falhe. O ciclo opera em três passos estritos:

1. **🔴 Red (Vermelho):** Escreva um teste pequeno que expressa o comportamento esperado da funcionalidade. O teste deve falhar (inclusive não compilar inicialmente).
2. **🟢 Green (Verde):** Escreva a quantidade mínima de código de produção suficiente para fazer o teste passar. Não se preocupe com perfeição neste momento.
3. **🔵 Refactor (Refatorar):** Melhore o design, elimine duplicações, renomeie variáveis e aplique padrões SOLID, mantendo a suíte de testes sempre verde.

---

## 2. Anatomia de um Teste: O Padrão AAA

Todo teste unitário deve seguir a estrutura em três blocos limpos:
- **Arrange (Preparar):** Instancia classes, define parâmetros e prepara o ambiente.
- **Act (Agir):** Executa o método ou operação sob teste.
- **Assert (Verificar):** Checa se o resultado obtido é exatamente o esperado.

```csharp
[Fact]
public void CalcularMedia_ComNotasValidas_DeveRetornarMediaAritmetica()
{
    // Arrange
    var calculadora = new CalculadoraNotas();
    decimal[] notas = [8.0m, 6.0m, 10.0m];

    // Act
    decimal media = calculadora.Calcular(notas);

    // Assert
    Assert.Equal(8.0m, media);
}
```

## 3. Facts vs. Theories no xUnit

- **`[Fact]`:** Teste unitário fixo, sem parâmetros, que valida um cenário invariável.
- **`[Theory]`:** Teste parametrizado executado repetidamente com conjuntos diferentes de entradas.

### Usando InlineData
Ideal para testar matrizes de decisão, regras de borda e validações numéricas:

```csharp
[Theory]
[InlineData(10.0, true)]
[InlineData(6.0, true)]
[InlineData(5.99, false)]
[InlineData(0.0, false)]
public void ValidarAprovacao_ComDiversasNotas_DeveClassificarCorretamente(decimal nota, bool esperadoAprovado)
{
    // Arrange & Act
    bool aprovado = AvaliadorAcademico.EstaAprovado(nota);

    // Assert
    Assert.Equal(esperadoAprovado, aprovado);
}
```

### Usando MemberData para Casos Complexos
Quando os dados de teste exigem instâncias de objetos ou coleções ricas:

```csharp
public static TheoryData<Curso, decimal> DadosCursosDesconto => new()
{
    { new Curso(1, "Fundamentos C#", 200m), 180m },
    { new Curso(2, "Arquitetura .NET", 500m), 450m },
};

[Theory]
[MemberData(nameof(DadosCursosDesconto))]
public void AplicarDescontoPadrao_DeveReduzirPrecoEmDezPorCento(Curso curso, decimal precoEsperado)
{
    var servico = new PrecificacaoService();
    decimal precoFinal = servico.AplicarDesconto(curso);

    Assert.Equal(precoEsperado, precoFinal);
}
```

## 4. Testando Exceções com Assert.Throws

Ao validar regras defensivas de domínio, verifique se a exceção correta é disparada com os dados esperados:

```csharp
[Fact]
public void CriarAluno_ComEmailInvalido_DeveLancarArgumentException()
{
    // Act & Assert
    var ex = Assert.Throws<ArgumentException>(() =>
    {
        _ = new Aluno(id: 1, nome: "Carlos", email: "email-invalido-sem-arroba");
    });

    Assert.Contains("E-mail inválido", ex.Message);
}
```

---

## 5. Boas Práticas de Nomenclatura e Design de Testes

1. **Nomes Semânticos:** Use o padrão `Metodo_Cenario_ResultadoEsperado` (ex: `Matricular_QuandoTurmaLotada_DeveLancarExcecao`).
2. **Testes Rápidos e Isolados:** Um teste unitário não deve depender de conexão de rede, sistema de arquivos real ou outro teste que tenha rodado antes.
3. **Apenas uma Ação por Teste:** O bloco `Act` deve invocar apenas um método do componente sob teste.
