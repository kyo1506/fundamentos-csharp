# Lição 05.5: Dublês de Teste (Fakes e Mocks), Cobertura e Engenharia de Software

Em sistemas profissionais, componentes de negócio interagem com persistência, APIs de terceiros e serviços assíncronos. Para testar a lógica sem acoplamento externo, usamos **Dublês de Teste (Test Doubles)** e ferramentas de análise de cobertura.

---

## 1. A Taxonomia dos Dublês de Teste

Gerard Meszaros categorizou cinco tipos de dublês de teste:

| Tipo | O que faz | Exemplo |
|---|---|---|
| **Dummy** | Objeto passado apenas para preencher parâmetros obrigatórios do construtor, sem nunca ser executado. | Passar um `ILogger` nulo ou vazio quando o teste não valida logs. |
| **Stub** | Fornece respostas pré-programadas para chamadas feitas durante o teste. | Retornar sempre `true` para `emailValidator.IsValid(email)`. |
| **Spy** | Um stub que grava o histórico de chamadas para verificação posterior. | Contabilizar quantas vezes o método `EnviarSms()` foi invocado. |
| **Fake** | Implementação funcional simplificada da interface (não recomendada para produção, mas ideal para testes). | Um repositório em memória com `Dictionary<int, T>` em vez de banco SQL. |
| **Mock** | Objeto pré-programado com expectativas de quais métodos devem ser chamados e com quais parâmetros específicos. | Configurado com bibliotecas como NSubstitute ou Moq. |

## 2. Construindo Fakes Manuais (A Abordagem Mais Robusta)

Em muitas situações, criar uma implementação Fake em memória é mais limpo, mais rápido e menos frágil do que configurar dezenas de linhas de mocks sintéticos:

```csharp
public class InMemoryAlunoRepository : IAlunoRepository
{
    private readonly Dictionary<int, Aluno> _alunos = new();

    public Task<Aluno?> ObterPorIdAsync(int id, CancellationToken ct = default)
    {
        _alunos.TryGetValue(id, out var aluno);
        return Task.FromResult(aluno);
    }

    public Task AdicionarAsync(Aluno aluno, CancellationToken ct = default)
    {
        _alunos[aluno.Id] = aluno;
        return Task.CompletedTask;
    }

    public Task<IReadOnlyList<Aluno>> ListarTodosAsync(CancellationToken ct = default)
    {
        return Task.FromResult<IReadOnlyList<Aluno>>(_alunos.Values.ToList());
    }
}
```

No teste de caso de uso:

```csharp
[Fact]
public async Task MatricularAluno_QuandoDadosValidos_DeveSalvarNoRepositorio()
{
    // Arrange
    var fakeRepo = new InMemoryAlunoRepository();
    var useCase = new CadastrarAlunoUseCase(fakeRepo);

    // Act
    var novoAluno = await useCase.ExecutarAsync(new NovoAlunoDto("Maria", "maria@teste.com"));

    // Assert
    var salvo = await fakeRepo.ObterPorIdAsync(novoAluno.Id);
    Assert.NotNull(salvo);
    Assert.Equal("Maria", salvo!.Nome);
}
```

## 3. Cobertura de Código com Coverlet

A cobertura de código mede a porcentagem de linhas, branches e métodos de produção exercitados pela suíte de testes. No .NET, utilizamos o coletor `coverlet.collector`:

```bash
dotnet test --collect:"XPlat Code Coverage"
```

### Regras Práticas de Cobertura
1. **Foco no Domínio e Aplicação:** A camada de regras de negócio deve ter meta de 90%+ de cobertura.
2. **Evite a Ilusão do 100%:** Testar DTOs anêmicos ou linhas de bootstrapping de framework apenas para inflar números gera testes inúteis e caros de manter.
3. **Branch Coverage:** Dê preferência à cobertura de ramificações (`if`, `switch`, ternários) em vez de apenas cobertura de linhas.

## 4. Práticas de Engenharia: Code Review, CI e PRs

1. **Pull Requests Focados:** PRs com menos de 400 linhas são revisados com 3 vezes mais eficácia do que PRs gigantescos.
2. **Pipelines de CI (Continuous Integration):** A cada push na branch do PR, a suíte de testes (`dotnet test`) e a verificação de compilação sem warnings devem rodar automaticamente antes do merge.
3. **Conventional Commits:** Padronize mensagens de commit para clareza no histórico do repositório (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`).
