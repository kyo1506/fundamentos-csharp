# Lição 04.1: Garbage Collector, IDisposable e Finalizadores

O .NET gerencia a alocação de memória automaticamente por meio do Garbage Collector (GC). No entanto, recursos externos (handles de arquivos, conexões de rede, ponteiros nativos de banco de dados) exigem liberação determinística. Compreender as gerações do GC e o padrão `IDisposable` é essencial para construir sistemas de alta confiabilidade.

---

## 1. Como o Garbage Collector Funciona

O GC do .NET opera em um heap gerenciado. Quando novos objetos são instanciados via `new`, a memória é alocada sequencialmente. O GC atua periodicamente para compactar e desalocar objetos inalcançáveis (sem referências vivas a partir de raízes de execução, como variáveis locais da pilha ou campos estáticos).

### O Modelo Geracional

O heap efêmero é dividido em três gerações lógicas baseadas na hipótese empírica de que objetos recém-criados tendem a ter vida curta:

1. **Geração 0 (Gen 0):** Onde quase todos os novos objetos de pequeno porte nascem. As coletas em Gen 0 são extremamente rápidas (fração de milissegundos) e frequentes.
2. **Geração 1 (Gen 1):** Funciona como uma zona de amortecimento. Objetos que sobrevivem a uma coleta em Gen 0 são promovidos para Gen 1.
3. **Geração 2 (Gen 2):** Contém objetos de longa duração (ex: caches estáticos, singletons, configurações de aplicação). Coletas de Gen 2 (Full GC) inspecionam todo o heap gerenciado e custam mais tempo de CPU.

### Heaps Especiais

- **LOH (Large Object Heap):** Objetos com tamanho igual ou superior a 85.000 bytes (como grandes arrays ou strings gigantes) são alocados diretamente no LOH para evitar o custo de cópia e compactação frequente em Gen 0. O LOH é coletado apenas durante coletas de Gen 2.
- **POH (Pinned Object Heap):** Criado para alocar buffers fixados em memória, evitando fragmentação do heap comum durante operações nativas ou de interoperabilidade de IO.

---

## 2. Recursos Gerenciados vs. Não Gerenciados

- **Recursos Gerenciados:** Memória de objetos C# padrão (arrays, instâncias de classes, strings). O GC os limpa sozinho.
- **Recursos Não Gerenciados:** Handles do sistema operacional (descritores de arquivos, sockets TCP, janelas gráficas, ponteiros C/C++). O GC não conhece as regras do sistema operacional para fechar esses ponteiros.

Se você apenas esperar o GC coletar uma classe que segura um descritor de arquivo aberto, o arquivo pode ficar travado indefinidamente no sistema operacional, causando erros de concorrência ou esgotamento de descritores.

## 3. O Padrão IDisposable

A interface `IDisposable` fornece um mecanismo explícito e determinístico para liberar recursos:

```csharp
public interface IDisposable
{
    void Dispose();
}
```

### O Comando `using` Moderno

A partir do C# 8, podemos usar a declaração `using var`, que garante que o método `Dispose()` seja invocado assim que a variável sair de escopo, mesmo diante de exceções:

```csharp
public void ProcessarArquivo(string caminho)
{
    using var leitor = new StreamReader(caminho);
    string? linha;
    while ((linha = leitor.ReadLine()) != null)
    {
        Console.WriteLine(linha);
    }
} // 'leitor.Dispose()' é chamado automaticamente aqui
```

## 4. O Padrão de Descarte Completo (Dispose Pattern)

Quando uma classe controla diretamente recursos não gerenciados ou subclasses que podem ser estendidas, adota-se o padrão canônico com `Dispose(bool disposing)`, finalizador e `GC.SuppressFinalize`:

```csharp
public class GerenciadorRecurso : IDisposable
{
    private bool _disposed = false;
    private IntPtr _ponteiroNativo; // Exemplo de recurso não gerenciado
    private SafeHandle? _safeHandle; // Recurso encapsulado

    public GerenciadorRecurso()
    {
        // Alocação de recursos
    }

    public void Dispose()
    {
        Dispose(disposing: true);
        // Avisa ao GC que os recursos já foram liberados: dispensa a chamada ao finalizador
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // 1. Liberar recursos gerenciados que implementam IDisposable
            _safeHandle?.Dispose();
        }

        // 2. Liberar recursos não gerenciados diretos
        if (_ponteiroNativo != IntPtr.Zero)
        {
            // Liberar memória nativa
            _ponteiroNativo = IntPtr.Zero;
        }

        _disposed = true;
    }

    // Finalizador (usado apenas como rede de segurança se o consumidor esquecer de chamar Dispose)
    ~GerenciadorRecurso()
    {
        Dispose(disposing: false);
    }
}
```

> **Atenção:** Em 99% das aplicações modernas de negócio, você não cria recursos nativos brutos, utiliza classes prontas que já implementam `IDisposable` (como `FileStream`, `HttpClient`, `DbContext`). Nesses casos, apenas implemente `IDisposable` simples repassando a chamada para os membros filhos sem necessidade de finalizador.

## 5. Descarte Assíncrono com IAsyncDisposable

Quando o fechamento de um recurso envolve IO de rede ou disco (ex: dar flush em buffer de escrita para disco ou fechar socket de forma limpa), o descarte síncrono pode bloquear a thread. Para isso, o .NET introduziu `IAsyncDisposable`:

```csharp
public interface IAsyncDisposable
{
    ValueTask DisposeAsync();
}
```

Uso prático:

```csharp
public async Task GravarDadosAsync(string caminho, byte[] dados)
{
    await using var stream = new FileStream(caminho, FileMode.Create, FileAccess.Write, FileShare.None, 4096, useAsync: true);
    await stream.WriteAsync(dados);
} // 'await stream.DisposeAsync()' executado ao fim do escopo
```

## 6. Boas Práticas de Memória

1. **Evite finalizadores desnecessários:** Objetos com finalizador sobrevivem pelo menos uma geração a mais no GC porque precisam passar pela fila de finalização (`Finalization Queue`).
2. **Sempre chame `GC.SuppressFinalize(this)`:** No método `Dispose()`, evite que o objeto vá para a fila de finalização.
3. **Prefira `using`:** Nunca confie em chamadas manuais soltas a `.Dispose()`, pois exceções antes da chamada geram vazamento de recursos.
4. **Cuidado com eventos:** Adicionar um listener a um evento estático ou de vida longa retém a instância consumidora viva na memória (memory leak clássico em C#). Cancele a inscrição com `-=` quando o ciclo de vida terminar.
