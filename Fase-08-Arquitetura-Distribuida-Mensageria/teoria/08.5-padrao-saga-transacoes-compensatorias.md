# 08.5: Padrão Saga e Transações Compensatórias

> **Fase 08: Arquitetura Distribuída e Mensageria** · Aula 5
> Objetivo: coordenar processos de negócio distribuídos entre múltiplos serviços independentes através de Sagas e ações de compensação.

---

## 1. O Fim das Transações ACID Globais

Em arquiteturas modernas com múltiplos bancos de dados independentes (um banco para o serviço Acadêmico, outro para o Financeiro e outro para o Catálogo), não é viável nem desejável abrir uma transação ACID abrangendo todos os bancos.

O padrão **Saga** (introduzido por Hector Garcia-Molina em 1987) estrutura uma transação de longa duração em uma sequência linear de transações locais em cada serviço:
- Cada etapa da Saga atualiza seu próprio banco de dados local.
- Se todas as etapas tiverem êxito, a transação distribuída é finalizada com sucesso.
- Se uma etapa intermediária falhar, a Saga dispara uma série de **ações compensatórias** (transações reversas) para desfazer os efeitos parciais nas etapas anteriores.

---

## 2. Coreografia vs Orquestração

Existem dois estilos principais para implementar uma Saga:

### A) Coreografia (Event-Driven Descentralizado)
- Não existe um coordenador central.
- Cada serviço escuta os eventos do serviço anterior e reage emitindo seus próprios eventos.
- **Vantagem:** baixo acoplamento.
- **Desvantagem:** difícil de rastrear o fluxo completo quando a complexidade aumenta (efeito "teia de aranha").

### B) Orquestração (Coordenador Central / State Machine)
- Um serviço central (Orquestrador) comanda explicitamente cada serviço envolvido:
  1. Manda reservar vaga.
  2. Manda processar pagamento.
  3. Manda gerar contrato.
- Se o pagamento falhar, o orquestrador comanda: "Cancele a reserva da vaga".
- **Vantagem:** fluxo explícito, fácil de auditar, monitorar e testar.
- **Desvantagem:** maior concentração de regras no orquestrador.

## 3. Exemplo Prático em C#: Máquina de Estados de Saga

```csharp
namespace EventBus.Distribuido.Core.Sagas;

public enum EstadoSaga
{
    Iniciada,
    VagaReservada,
    PagamentoConfirmado,
    Concluida,
    Falha,
    Compensada
}

public sealed class MatriculaSagaContexto
{
    public Guid SagaId { get; init; } = Guid.NewGuid();
    public int AlunoId { get; init; }
    public int CursoId { get; init; }
    public decimal Valor { get; init; }
    public EstadoSaga Estado { get; set; } = EstadoSaga.Iniciada;
    public List<string> HistoricoEtapas { get; } = new();

    public void RegistrarEtapa(string etapa)
    {
        HistoricoEtapas.Add($"{DateTime.UtcNow:HH:mm:ss} - {etapa}");
    }
}
```

### Orquestrador com Compensação

```csharp
public sealed class OrquestradorMatriculaSaga
{
    public async Task<bool> ExecutarSagaAsync(MatriculaSagaContexto contexto, bool simularFalhaPagamento = false)
    {
        contexto.RegistrarEtapa("Iniciando Saga de Matrícula.");

        // Passo 1: Reserva de Vaga
        contexto.Estado = EstadoSaga.VagaReservada;
        contexto.RegistrarEtapa("Vaga reservada no curso.");

        // Passo 2: Cobrança / Pagamento
        if (simularFalhaPagamento)
        {
            contexto.Estado = EstadoSaga.Falha;
            contexto.RegistrarEtapa("Falha no pagamento: saldo insuficiente.");

            // Ação Compensatória: Desfazer a reserva de vaga!
            await CompensarReservaAsync(contexto);
            contexto.Estado = EstadoSaga.Compensada;
            contexto.RegistrarEtapa("Compensação concluída: vaga liberada no catálogo.");
            return false;
        }

        contexto.Estado = EstadoSaga.PagamentoConfirmado;
        contexto.RegistrarEtapa("Pagamento efetuado com sucesso.");

        // Passo 3: Conclusão
        contexto.Estado = EstadoSaga.Concluida;
        contexto.RegistrarEtapa("Matrícula efetivada com sucesso.");
        return true;
    }

    private Task CompensarReservaAsync(MatriculaSagaContexto ctx)
    {
        // Lógica de liberação da vaga no catálogo acadêmico
        return Task.CompletedTask;
    }
}
```

## 4. Anti-exemplo: Compensação sem Idempotência

Em sistemas reais, a própria ação de compensação (o cancelamento) pode falhar na rede e precisar ser reenviada. Portanto:
- **Toda ação compensatória DEVE ser rigorosamente idempotente.**
- Cancelar uma reserva já cancelada deve retornar sucesso sem alterar o estado do sistema.

2. **Médio:** Implemente uma Saga com 3 passos onde o passo 3 falha, demonstrando a execução ordenada das compensações dos passos 2 e 1 em ordem inversa (Stack LIFO).
