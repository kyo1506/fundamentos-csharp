# 08.1: Sistemas Distribuídos e Comunicação Assíncrona

> **Fase 08: Arquitetura Distribuída e Mensageria** · Aula 1
> Objetivo: compreender as falácias da computação distribuída, o desacoplamento temporal e as vantagens da comunicação assíncrona orientada a eventos.

---

## 1. Do Monolito aos Sistemas Distribuídos

Em uma aplicação monolítica típica, invocar uma funcionalidade de outro domínio é uma chamada de método em memória (in-process). O ponteiro da pilha avança, os parâmetros são passados por registrador ou referência e, salvo falha catastrófica de hardware ou falta de memória, a chamada completa em nanossegundos com certeza matemática de entrega.

Quando dividimos um sistema em múltiplos serviços distribuídos (microsserviços, workers, filas), a comunicação cruza as fronteiras do processo e viaja por uma rede física (TCP/IP).

### As Falácias da Computação Distribuída
L. Peter Deutsch formulou as célebres falácias que todo arquiteto .NET precisa internalizar:
1. A rede é confiável (não é: pacotes caem, timeouts acontecem).
2. A latência é zero (não é: chamadas de rede demoram ordens de grandeza a mais que chamadas em memória).
3. A largura de banda é infinita.
4. A rede é segura.
5. A topologia não muda.
6. Há apenas um administrador.
7. O custo de transporte é zero.
8. A rede é homogênea.

## 2. Acoplamento Temporal vs Desacoplamento Temporal

### Comunicação Síncrona (HTTP/REST ou gRPC)
Quando o Serviço A faz um `POST` HTTP para o Serviço B e aguarda a resposta antes de prosseguir, temos **acoplamento temporal**:
- O Serviço B precisa estar ativo e saudável exatamente no mesmo milissegundo em que o Serviço A dispara a requisição.
- Se o Serviço B estiver lento ou fora do ar, o Serviço A trava suas threads de requisição e cascateia a lentidão para os clientes.

### Comunicação Assíncrona Orientada a Eventos
Na comunicação assíncrona orientada a eventos:
- O Serviço A emite uma mensagem informando que um fato do domínio ocorreu (`AlunoMatriculadoEvent`).
- A mensagem é depositada em um intermediário confiável (Message Broker).
- O Serviço B consome e processa o evento no seu próprio ritmo, mesmo que esteja temporariamente indisponível no momento da emissão.
- Obtemos **desacoplamento temporal** e resiliência contra indisponibilidades parciais.

## 3. Exemplo Prático em C#: Contrato Imutável de Evento

Em C# moderno (.NET 10), eventos distribuídos devem ser modelados como registros (`record`) imutáveis, contendo identificador único (`Guid`), data e hora em formato UTC e a versão do esquema.

```csharp
namespace EventBus.Distribuido.Core.Modelos;

/// <summary>Contrato base para eventos de domínio distribuídos.</summary>
public record EventoDistribuido(
    Guid EventId,
    DateTime OccurredOnUtc,
    string EventType
);

/// <summary>Evento emitido quando uma nova matrícula é concluída.</summary>
public sealed record AlunoMatriculadoEvento(
    Guid EventId,
    DateTime OccurredOnUtc,
    int AlunoId,
    string NomeAluno,
    string EmailAluno,
    int CursoId
) : EventoDistribuido(EventId, OccurredOnUtc, nameof(AlunoMatriculadoEvento))
{
    public static AlunoMatriculadoEvento Criar(int alunoId, string nome, string email, int cursoId)
        => new(Guid.NewGuid(), DateTime.UtcNow, alunoId, nome, email, cursoId);
}
```

## 4. Anti-exemplo: Dependência em Cascata Síncrona

```csharp
// ANTI-EXEMPLO: se qualquer serviço externo falhar, toda a operação é perdida!
public async Task MatricularAlunoAsync(MatriculaRequest req)
{
    await _db.SalvarMatriculaAsync(req);
    
    // Chamada síncrona 1: serviço financeiro
    await _httpFinanceiro.PostAsync("/faturamento", ...); // se der timeout aqui, o aluno já foi salvo?
    
    // Chamada síncrona 2: serviço de envio de email
    await _httpEmail.PostAsync("/boas-vindas", ...); // se der 500, a transação quebra?
}
```

O problema desse anti-exemplo é a fragilidade: a probabilidade de falha da operação é multiplicada pelo número de dependências em cadeia. A solução arquitetural correta é salvar a matrícula localmente e publicar o evento para que o financeiro e o envio de email processem assincronamente.

## 5. Exercícios de Fixação

1. **Fácil:** Escreva um método estático que valide se um evento possui `EventId` válido e data em UTC dentro de uma janela de tolerância de até 5 minutos em relação à hora atual.
2. **Médio:** Crie uma classe utilitária que calcule a disponibilidade composta de um sistema encadeado: dadas as disponibilidades de 3 microsserviços chamados síncronamente (ex: 99%, 99% e 95%), demonstre como a disponibilidade final despenca.
3. **Desafiador:** Projete a interface de um despachante de eventos assíncrono em C# que distribua uma mensagem para uma lista de consumidores registrados sem bloquear o remetente.
