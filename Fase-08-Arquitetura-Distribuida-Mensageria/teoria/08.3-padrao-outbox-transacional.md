# 08.3: Padrão Outbox Transacional (Transactional Outbox Pattern)

> **Fase 08: Arquitetura Distribuída e Mensageria** · Aula 3
> Objetivo: resolver definitivamente o problema de Dual-Write garantindo atomicidade entre o banco de dados relacional e o envio de mensagens para a rede.

---

## 1. O Problema do Dual-Write

Imagine o seguinte código comum em sistemas corporativos:

```csharp
using var transaction = await _db.Database.BeginTransactionAsync();

_db.Matriculas.Add(novaMatricula);
await _db.SaveChangesAsync();

// Dual-write: estamos tentando falar com DOIS sistemas independentes!
await _eventBus.PublicarAsync(new AlunoMatriculadoEvento(...));

await transaction.CommitAsync();
```

O que acontece se:
1. O banco comita com sucesso, mas a rede cai exatamente antes do `_eventBus.PublicarAsync`? O aluno foi matriculado no banco, mas nenhum serviço consumidor ficou sabendo!
2. O evento é publicado com sucesso no broker, mas o `transaction.CommitAsync()` falha por conflito de concorrência ou timeout? O evento foi enviado para o mundo externo, mas o dado NUNCA existiu no banco! Inconsistência irreparável.

Transações distribuídas de duas fases (Two-Phase Commit ou 2PC) não funcionam em arquiteturas de nuvem modernas devido à alta latência e bloqueios em rede.

---

## 2. A Solução: Transactional Outbox Pattern

O padrão Outbox Transacional resolve essa equação utilizando uma única transação ACID local no banco de dados relacional:

```
[Requisição HTTP]
        │
        ▼
[Transação ACID Local no Banco]
 ├─ 1. Grava a Entidade de Negócio (ex: AlunoMatriculado)
 └─ 2. Grava a Mensagem na Tabela OutboxMessages (status: Pendente)
        │ (Commit 100% atômico e garantido)
        ▼
[Worker Assíncrono em Segundo Plano]
 ├─ Lê periodicamente registros pendentes na tabela OutboxMessages
 ├─ Publica cada mensagem no Message Broker
 └─ Marca o registro como Publicado (ou incrementa falha e retenta)
```

### Estrutura da Tabela de Outbox

```csharp
namespace EventBus.Distribuido.Core.Outbox;

public sealed class MensagemOutbox
{
    public Guid Id { get; set; } = Guid.NewGuid();
    public string TipoEvento { get; set; } = string.Empty;
    public string PayloadJson { get; set; } = string.Empty;
    public DateTime CriadoEmUtc { get; set; } = DateTime.UtcNow;
    public DateTime? PublicadoEmUtc { get; set; }
    public string Status { get; set; } = StatusOutbox.Pendente;
    public int Tentativas { get; set; } = 0;
    public string? UltimoErro { get; set; }
}

public static class StatusOutbox
{
    public const string Pendente = "Pendente";
    public const string Publicado = "Publicado";
    public const string Falha = "Falha";
}
```

---

## 3. Garantia de Entrega: At-Least-Once (Pelo Menos Uma Vez)

O Outbox Pattern provê garantia de entrega **At-Least-Once**:
- A mensagem tem a garantia de ser entregue pelo menos uma vez.
- Em cenários extremos (ex: o worker publica no broker, mas o container desliga antes de atualizar a linha para `Publicado`), o worker religará e publicará a mensagem novamente.
- Isso significa que mensagens duplicadas PODEM acontecer, exigindo que o lado consumidor seja obrigatoriamente **idempotente** (tema da próxima aula).

## 4. Anti-exemplo: Polling Agressivo sem Paginação nem Bloqueio

```csharp
// ANTI-EXEMPLO: lê a tabela inteira sem limite e trava o banco relacional
while (true)
{
    var pendentes = await _db.OutboxMessages.Where(m => m.Status == "Pendente").ToListAsync();
    foreach (var msg in pendentes) { ... }
    // Sem delay ou lendo 50 mil linhas de uma vez na memória!
}
```

**Boas Práticas:**
- Paginar a leitura (`Take(50)` ou `Take(100)`).
- Utilizar índice composto no banco por `(Status, CriadoEmUtc)`.
- Adicionar intervalo saudável de descanso (`Task.Delay`) ou gatilhos com `System.Threading.Channels` para despachos em tempo quase real.
