## 1. Topologia de Message Brokers

Um Message Broker atua como o correio postal inteligente do ecossistema corporativo. Em tecnologias como o RabbitMQ, a arquitetura se divide em três elementos essenciais:

1. **Exchange (Central de Distribuição):** recebe as mensagens dos produtores e decide para quais filas encaminhar, com base em regras de ligação (bindings).
   - **Direct Exchange:** roteamento exato baseado em uma chave de roteamento (Routing Key exata).
   - **Fanout Exchange:** transmissão em broadcast (entrega uma cópia para todas as filas conectadas, ignorando a chave).
   - **Topic Exchange:** roteamento dinâmico com padrões de curingas (ex: `financeiro.*` ou `aluno.#`).
2. **Queue (Fila):** estrutura bufferizada em memória ou disco que armazena as mensagens ordenadamente até que um consumidor as processe.
3. **Bindings:** os elos que conectam Exchanges às Filas, definindo os critérios de entrega.

## 2. Abstração de Barramento (`IEventBus`)

Em projetos .NET profissionais, a aplicação não deve se acoplar diretamente às classes do driver de mensageria (como o SDK cru do RabbitMQ ou Kafka). Criamos ou utilizamos abstrações de alto nível (como o MassTransit ou uma interface limpa de domínio `IEventBus`):

```csharp
namespace EventBus.Distribuido.Core.Barramento;

public interface IEventBus
{
    Task PublicarAsync<T>(T evento, CancellationToken ct = default) where T : class;
    void RegistrarConsumidor<T, TConsumer>() 
        where T : class 
        where TConsumer : IConsumidorEvento<T>;
}

public interface IConsumidorEvento<in T> where T : class
{
    Task ConsumirAsync(T mensagem, CancellationToken ct = default);
}
```

## 3. Resiliência: Dead-Letter Queue (DLQ) e Políticas de Retentativa

Quando um consumidor falha ao processar uma mensagem (ex: banco de dados do consumidor caiu), o broker precisa saber o que fazer:
1. **Immediate Retry (Retentativa Imediata):** tenta reexecutar até 3 vezes com intervalo curto ou exponencial (backoff).
2. **Dead-Letter Queue (Fila de Mensagens Mortas):** se a mensagem persistir em falha após o limite máximo de tentativas configurado, ela não deve travar a fila principal. A mensagem é redirecionada para a DLQ para auditoria humana ou reprocessamento posterior via job administrativo.

```csharp
public sealed class PoliticaRetentativa
{
    public int MaximoTentativas { get; } = 3;
    public TimeSpan DelayBase { get; } = TimeSpan.FromMilliseconds(200);

    public bool DeveEnviarParaDlq(int tentativasAtuais)
        => tentativasAtuais >= MaximoTentativas;
}
```

## 4. Anti-exemplo: Consumidor Bloqueante e Perda de ACK

```csharp
// ANTI-EXEMPLO: confirmar recebimento antes de processar com sucesso!
channel.BasicConsume(queue: "pedidos", autoAck: true, consumer: (model, ea) =>
{
    // Se o processo for encerrado aqui (kill -9, falha de container no Render),
    // a mensagem foi confirmada no broker, mas NUNCA foi gravada no banco! Perda de dados!
    ProcessarPedido(ea.Body);
});
```

**Regra de Ouro:** Nunca use `autoAck: true` em sistemas críticos. O envio de confirmação (`Ack`) só deve ser transmitido ao broker após o efeito colateral de negócio ser concluído e persistido.
