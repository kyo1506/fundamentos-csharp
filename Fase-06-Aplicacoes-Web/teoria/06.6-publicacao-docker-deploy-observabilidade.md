# Lição 06.6: Publicação, Contêineres Docker, Deploy e Health Checks

Construir o código de uma Web API é apenas a primeira metade do ciclo de vida de uma aplicação. A outra metade consiste em empacotá-la de forma imutável, testável e pronta para execução em ambientes de nuvem, Kubernetes e contêineres Docker.

---

## 1. Publicação Nativa com o dotnet CLI

Para compilar e otimizar binários para produção:

```bash
# Compilação em modo Release pronta para implantação
dotnet publish -c Release -o ./publish

# Publicação Self-Contained para Linux (inclui o runtime .NET no binário)
dotnet publish -c Release -r linux-x64 --self-contained true -o ./publish-linux
```

---

## 2. Dockerfile Multi-Stage Otimizado

O padrão Multi-Stage Build separa o ambiente de compilação (pesado, com o SDK completo) da imagem de execução final (leve, contendo apenas o runtime e os binários compilados):

```dockerfile
# ----------------------------------------------------
# Estágio 1: Build (SDK Completo)
# ----------------------------------------------------
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

# Copia arquivos de projeto e restaura dependências (aproveita cache de camadas)
COPY ["aplicacao/GestaoAcademica.WebApi.csproj", "aplicacao/"]
RUN dotnet restore "aplicacao/GestaoAcademica.WebApi.csproj"

# Copia o restante do código e compila
COPY . .
WORKDIR "/src/aplicacao"
RUN dotnet publish "GestaoAcademica.WebApi.csproj" -c Release -o /app/publish /p:UseAppHost=false

# ----------------------------------------------------
# Estágio 2: Runtime Final (Imagem Mínima e Segura)
# ----------------------------------------------------
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app
EXPOSE 8080

# Execução como usuário não-root por segurança
USER app

COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "GestaoAcademica.WebApi.dll"]
```

### Vantagens do Multi-Stage Build
1. **Segurança:** O compilador, ferramentas de build e código-fonte bruto não vão para a imagem final de produção.
2. **Tamanho Reduzido:** A imagem final cai de ~800 MB para ~110 MB.
3. **Velocidade de Deploy:** Menor tempo de download nos clusters e menor superfície de ataque para vulnerabilidades (CVEs).

## 3. Health Checks para Liveness e Readiness Probes

Orquestradores de contêineres (como Kubernetes, Docker Swarm ou serviços gerenciados de nuvem) monitoram a saúde da aplicação através de sondas HTTP:

```csharp
var builder = WebApplication.CreateBuilder(args);

// Adiciona serviço de verificação de saúde
builder.Services.AddHealthChecks();

var app = builder.Build();

// Endpoint de saúde lido pelo orquestrador
app.MapHealthChecks("/healthz");

app.Run();
```

Quando a aplicação estiver inicializada e saudável, acessar `GET /healthz` retorna `200 OK` com o texto `Healthy`.

## 4. Configuração por Variáveis de Ambiente em Contêineres

Em ambientes de contêineres e nuvem, nunca grave segredos ou strings de conexão no código ou em arquivos versionados no Git. O ASP.NET Core mapeia automaticamente variáveis de ambiente para a árvore de configuração:

- Chave JSON: `ConnectionStrings:DefaultConnection`
- Variável de Ambiente Linux/Docker: `ConnectionStrings__DefaultConnection` (use dois underlines `__`)

```bash
docker run -d -p 8080:8080 \
  -e ConnectionStrings__DefaultConnection="Data Source=banco.db" \
  -e Jwt__ChaveSecreta="MinhaChaveUltraSeguraParaProducao123!" \
  minha-api:latest
```
