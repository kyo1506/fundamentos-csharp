# Lição 06.3: Pipeline de Middlewares e Padronização de Erros com ProblemDetails

No ASP.NET Core, toda requisição HTTP recebida e toda resposta enviada transitam através de uma esteira bidirecional de componentes encadeados chamada **Pipeline de Middlewares**. Entender a ordem e a responsabilidade de cada middleware é fundamental para a estabilidade e a segurança da aplicação.

---

## 1. O Funcionamento do Pipeline Bidirecional

Cada middleware tem duas oportunidades de interagir com o ciclo de vida da requisição:
1. **Na descida:** Antes que o próximo middleware ou o endpoint seja invocado.
2. **Na subida:** Depois que o endpoint final executou e gerou a resposta.

```
Requisição HTTP ────────┐
                       ▼
             [ Middleware 1 (Logging) ]
                       │
                       ▼
             [ Middleware 2 (Autenticação) ]
                       │
                       ▼
             [ Middleware 3 (Roteamento / Endpoint) ]
                       │
                       ▼
                   [ Handler ]
                       │
                       ▼ (Gera Resposta)
             [ Middleware 2 (Auditoria pós) ]
                       │
                       ▼
             [ Middleware 1 (Finaliza medição) ]
                       │
Resposta HTTP ◄────────┘
```

Se algum middleware interromper o fluxo (short-circuit), como ao rejeitar uma requisição não autenticada (`401`), os componentes seguintes sequer são executados.

---

## 2. Ordem Canônica de Middlewares

A ordem de registro dos middlewares no `Program.cs` importa diretamente. A sequência canônica recomendada pela Microsoft é:

```csharp
var app = builder.Build();

// 1. Tratamento Global de Exceções (deve ser o primeiro da pilha)
app.UseExceptionHandler();

// 2. HTTPS Redirection e HSTS
app.UseHttpsRedirection();

// 3. Arquivos Estáticos (caso sirva SPAs ou imagens)
app.UseStaticFiles();

// 4. Roteamento
app.UseRouting();

// 5. CORS (Cross-Origin Resource Sharing)
app.UseCors();

// 6. Autenticação (Quem é você?)
app.UseAuthentication();

// 7. Autorização (O que você pode fazer?)
app.UseAuthorization();

// 8. Endpoints finais
app.MapControllers(); // ou app.MapGet(...)
```

## 3. Criando um Middleware Customizado

Podemos criar middlewares customizados para tarefas transversais como rastreamento de correlação (`Correlation ID`) ou medição de latência:

```csharp
public class CorrelationIdMiddleware
{
    private readonly RequestDelegate _next;
    private const string HeaderCorrelationId = "X-Correlation-Id";

    public CorrelationIdMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        if (!context.Request.Headers.TryGetValue(HeaderCorrelationId, out var correlationId))
        {
            correlationId = Guid.NewGuid().ToString();
            context.Request.Headers.Append(HeaderCorrelationId, correlationId);
        }

        context.Response.Headers.Append(HeaderCorrelationId, correlationId);

        // Chama o próximo middleware da esteira
        await _next(context);
    }
}

// Extensão utilitária:
public static class MiddlewareExtensions
{
    public static IApplicationBuilder UseCorrelationId(this IApplicationBuilder app) =>
        app.UseMiddleware<CorrelationIdMiddleware>();
}
```

## 4. O Padrão RFC 7807 / RFC 9457: ProblemDetails

No passado, cada API retornava erros em formatos proprietários e inconsistentes (às vezes string pura, às vezes `{ "error": "msg" }`, outras `{ "mensagem": "..." }`).

A especificação IETF **Problem Details for HTTP APIs** padroniza a estrutura JSON de erros:

```json
{
  "type": "https://api.faculdade.com/erros/vagas-esgotadas",
  "title": "Vagas Esgotadas",
  "status": 409,
  "detail": "As vagas para o curso 'Arquitetura .NET' estão totalmente esgotadas.",
  "instance": "/api/v1/matriculas"
}
```

### Habilitando ProblemDetails Nativo no ASP.NET Core

A partir do .NET 7/8, basta uma linha de configuração para o framework gerar `ProblemDetails` automaticamente para todos os erros 4xx e 5xx:

```csharp
builder.Services.AddProblemDetails();

var app = builder.Build();
app.UseExceptionHandler(); // Traduz exceções não tratadas para ProblemDetails 500 sem vazar stack trace
app.UseStatusCodePages();  // Traduz códigos 404, 401 sem corpo para ProblemDetails
```

### Manipulador Global Customizado com IExceptionHandler

No .NET 8+, podemos capturar exceções de domínio e transformá-las em respostas HTTP sem blocos `try/catch` manuais espalhados pelos endpoints:

```csharp
public class DomainExceptionHandler : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken cancellationToken)
    {
        if (exception is not DomainException domainEx)
        {
            return false; // Deixa outros handlers ou o fallback 500 processarem
        }

        var problemDetails = new ProblemDetails
        {
            Status = StatusCodes.Status409Conflict,
            Title = "Violação de Regra de Negócio",
            Detail = domainEx.Message,
            Instance = httpContext.Request.Path
        };

        httpContext.Response.StatusCode = StatusCodes.Status409Conflict;
        await httpContext.Response.WriteAsJsonAsync(problemDetails, cancellationToken);

        return true; // Exceção tratada com sucesso
    }
}

// Registro no container:
builder.Services.AddExceptionHandler<DomainExceptionHandler>();
builder.Services.AddProblemDetails();
```
