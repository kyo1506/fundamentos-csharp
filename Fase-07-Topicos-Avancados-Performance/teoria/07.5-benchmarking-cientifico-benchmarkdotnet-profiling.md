# 07.5 Benchmarking Científico com BenchmarkDotNet e Profiling

## Introdução: A Falácia do `Stopwatch`

Medir desempenho de software em ambientes gerenciados como o .NET Runtime (CoreCLR) é uma tarefa repleta de armadilhas sutis. Desenvolvedores frequentemente recorrem à classe `System.Diagnostics.Stopwatch` para cronometrar a execução de blocos de código:

```csharp
var sw = Stopwatch.StartNew();
ExecutarOperacao();
sw.Stop();
Console.WriteLine($"Tempo: {sw.ElapsedMilliseconds} ms");
```

Embora pareça intuitivo, essa abordagem é metodologicamente falha para microbenchmarking e engenharia de precisão pelos seguintes fatores:

1. **JIT Compilation (Cold vs. Warm):** A primeira execução compila o código IL para código de máquina na camada inicial (Tier 0). Medir a primeira chamada mede o custo do JIT, não a eficiência algorítmica do código otimizado.
2. **Tiered Compilation e OSR (On-Stack Replacement):** O runtime do .NET re-otimiza métodos quentes para a camada Tier 1 e aplica Dynamic PGO (Profile-Guided Optimization). Sem rodar dezenas de milhares de iterações de aquecimento (warmup), o código medido não reflete o estado final de produção.
3. **Pausas do Garbage Collector:** Se uma coleta de lixo (GC Gen 0, Gen 1 ou Gen 2) ocorrer durante o intervalo cronometrado, o tempo da pausa será indevidamente atribuído ao método sob teste.
4. **Precisão de Timer do Sistema Operacional:** O relógio do SO sofre com flutuações de clock, escalonamento preemptivo de threads e variações de estado de energia do processador (C-states e P-states).

Para transformar a medição de desempenho em uma disciplina científica rigorosa, o ecossistema .NET adota o padrão da indústria: a biblioteca **BenchmarkDotNet**.

## BenchmarkDotNet: A Ferramenta Padrão da Indústria

O BenchmarkDotNet isola o ambiente de execução executando o benchmark em um processo dedicado recém-iniciado, realiza centenas de iterações piloto para calcular o número ideal de operações por iteração, executa ciclos de aquecimento (warmup iterations) e aplica cálculos estatísticos rigorosos (média, desvio padrão, mediana, intervalo de confiança).

### Estrutura Básica de um Benchmark

```csharp
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]
public class ParsingBenchmark
{
    private string _registro = "2026-10-04|10:30:00|INFO|AUTH|Usuario autenticado com sucesso|200";

    [Benchmark(Baseline = true)]
    public (string Timestamp, string Nivel, int Codigo) ParsingLegadoStringSplit()
    {
        string[] partes = _registro.Split('|');
        return (partes[0], partes[2], int.Parse(partes[5]));
    }

    [Benchmark]
    public (string Timestamp, string Nivel, int Codigo) ParsingSpanZeroAlloc()
    {
        ReadOnlySpan<char> span = _registro.AsSpan();

        int primeiroPipe = span.IndexOf('|');
        ReadOnlySpan<char> timestamp = span.Slice(0, primeiroPipe);

        int segundoPipe = span.Slice(primeiroPipe + 1).IndexOf('|') + primeiroPipe + 1;
        int terceiroPipe = span.Slice(segundoPipe + 1).IndexOf('|') + segundoPipe + 1;
        ReadOnlySpan<char> nivel = span.Slice(segundoPipe + 1, terceiroPipe - segundoPipe - 1);

        int ultimoPipe = span.LastIndexOf('|');
        ReadOnlySpan<char> codigoSpan = span.Slice(ultimoPipe + 1);
        int codigo = int.Parse(codigoSpan);

        return (timestamp.ToString(), nivel.ToString(), codigo);
    }
}

public class Program
{
    public static void Main(string[] args)
    {
        BenchmarkRunner.Run<ParsingBenchmark>();
    }
}
```

## O Diagnóstico de Memória: `[MemoryDiagnoser]`

Em sistemas de alta concorrência e baixa latência, o consumo de CPU é apenas metade da equação. A taxa de alocação de memória no Heap gerenciado impacta diretamente a frequência de coletas do Garbage Collector.

Ao decorar a classe de benchmark com `[MemoryDiagnoser]`, o BenchmarkDotNet ativa os provedores de evento do ETW/EventPipe para monitorar:
- **Allocated:** Quantidade total de bytes alocados no Heap gerenciado por operação.
- **Gen 0 / Gen 1 / Gen 2:** Estimativa do número de coletas de cada geração do GC a cada 1.000 operações.

### Exemplo de Tabela de Resultados

| Method | Mean | Error | StdDev | Ratio | Gen0 | Allocated | Alloc Ratio |
|---|---|---|---|---|---|---|---|
| ParsingLegadoStringSplit | 85.42 ns | 0.82 ns | 0.77 ns | 1.00 | 0.0381 | 240 B | 1.00 |
| ParsingSpanZeroAlloc | 22.15 ns | 0.18 ns | 0.16 ns | 0.26 | 0.0153 | 96 B | 0.40 |

A análise acima evidencia que a abordagem utilizando `ReadOnlySpan<char>` reduziu o tempo de CPU em 74% e as alocações no heap em 60%.

## JIT Tiering, OSR e Dynamic PGO

O runtime moderno do .NET emprega compilação em camadas:

1. **Tier 0 (Quick JIT):** Gera código rapidamente sem realizar otimizações agressivas (sem inlining de métodos complexos, sem desdobramento de loops) para garantir inicialização rápida da aplicação.
2. **Tier 1 (Optimized JIT):** Quando um método atinge uma contagem limite de invocações (normalmente 30 vezes), o runtime re-enfileira o método para recompilação com todas as otimizações habilitadas.
3. **Dynamic PGO (Profile-Guided Optimization):** Introduzido e aprimorado no .NET 8 e .NET 9, insere sondas no Tier 0 para coletar perfis reais de execução (por exemplo, tipos concretos de interfaces mais comuns). No Tier 1, o compilador usa esses dados para devirtualizar chamadas e fazer inlining especulativo de código monomórfico.

Para que o BenchmarkDotNet teste o código no ápice de sua otimização, ele garante que os benchmarks sejam executados no modo de compilação otimizado (`Release`) com as camadas JIT totalmente estabilizadas.

## Profiling e Diagnósticos no .NET: Ferramentas CLI

Além dos microbenchmarks analíticos, sistemas em execução exigem ferramentas de amostragem de chamadas (CPU profiling) e inspeção de vazamentos de memória (memory dumps).

O ecossistema .NET dispõe de ferramentas de linha de comando multiplataforma:

1. **`dotnet-trace`:** Captura traces de CPU usando eventos EventPipe sem a necessidade de instrumentar o código-fonte, exportando arquivos `.nettrace` ou `.speedscope.json` para visualização em diagramas de chama (Flamegraphs).
   ```bash
   dotnet-trace collect --process-id <PID> --providers Microsoft-DotNETCore-SampleProfiler
   ```
2. **`dotnet-dump`:** Captura e analisa dumps de processo (heap, threads, chamadas de métodos bloqueadas) em ambientes Linux ou contêineres sem necessidade de depurador nativo acoplado.
   ```bash
   dotnet-dump collect --process-id <PID>
   dotnet-dump analyze dump_20261004.dmp
   ```
3. **`dotnet-gcdump`:** Coleta dumps leves focados na conectividade dos objetos no Heap gerenciado, permitindo identificar retenções de memória e referências circulares em gráficos de objetos.
   ```bash
   dotnet-gcdump collect --process-id <PID>
   ```

## Boas Práticas e Regras de Ouro de Benchmarking

1. **Sempre compilar em Release:** Benchmarks em modo `Debug` geram código IL com instruções de depuração (como `nop`) e desativam inlining do compilador, produzindo resultados distorcidos e sem valor prático.
2. **Evitar Dead Code Elimination:** Compiladores JIT otimizados eliminam cálculos cujos resultados não são consumidos. Sempre retorne o valor computado do método com `[Benchmark]` ou utilize `BenchmarkDotNet.Engines.Consumer`.
3. **Isolamento de Ambiente:** Evite rodar benchmarks enquanto outras aplicações pesadas (navegadores com dezenas de abas, compilações em paralelo) disputam ciclos de CPU e barramento de memória.
4. **Métricas Estáveis:** Valores de desvio padrão superiores a 5% da média sinalizam ruído externo ou dependência oculta de I/O na rotina sob teste.
