# 00.2 — Preparando o ambiente .NET

> **Fase 00** · Aula 2
> Objetivo: instalar o .NET, conhecer a CLI e criar/rodar seu primeiro programa.

## 1. O que você precisa

| Ferramenta | Para quê |
|------------|----------|
| **.NET SDK** | compilar, rodar e testar (`dotnet`) |
| **Editor** | escrever código (VS Code + extensão C#, ou JetBrains Rider) |
| **Git** | versionar e entregar via PR |

### Instalar o SDK
Baixe o **.NET SDK** (LTS/atual) em https://dotnet.microsoft.com/download.
No terminal, confirme:

```bash
dotnet --version          # ex.: 10.0.x
dotnet --list-sdks        # SDKs instalados
```

> ⚠️ **SDK ≠ Runtime.** Você precisa do **SDK** para compilar. O runtime vem junto no SDK.

## 2. A interface de linha de comando (CLI do .NET)

A CLI é a porta de entrada para tudo no .NET. Comandos que você usará sempre:

```bash
dotnet new console -n MeuApp        # cria um projeto console
dotnet new sln -n Curso             # cria uma solução
dotnet sln add MeuApp               # adiciona projeto à solução
dotnet build                        # compila (mostra erros/avisos)
dotnet run                          # compila e executa
dotnet test                         # roda os testes
dotnet publish -c Release           # gera a versão de publicação
```

### Solução vs Projeto
- **Projeto** (`*.csproj`): uma unidade compilável (um app, uma biblioteca, um projeto de testes).
- **Solução** (`*.sln`/`*.slnx`): um "guarda-chuva" que agrupa vários projetos relacionados.
- Organizar por solução facilita compilar/testar tudo de uma vez.

## 3. Seu primeiro programa

```bash
mkdir Primeiro && cd Primeiro
dotnet new console
```

O template gera um `Program.cs`:

```csharp
Console.WriteLine("Hello, World!");
```

Para executar:
```bash
dotnet run
# Hello, World!
```

### Estrutura de um projeto console
```
Primeiro/
├── Primeiro.csproj     # metadados: SDK, alvo (.NET), opções
├── Program.cs          # ponto de entrada
├── obj/                # temporários de compilação (não versionar)
└── bin/                # binários gerados (não versionar)
```

> `bin/` e `obj/` **não** devem ir para o Git (estão no `.gitignore`).

## 4. Conhecendo o `.csproj`

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>
</Project>
```

- `OutputType=Exe` → aplicação executável (console). `Library` → biblioteca.
- `TargetFramework` → qual versão do .NET (ex.: `net10.0`).
- `Nullable=enable` → avisos de possibilidade de nulo (ajuda a evitar bugs; usaremos sempre).
- `ImplicitUsings=enable` → vários `using` comuns já inclusos automaticamente.

## 5. Armadilhas comuns do começo

- ❌ Rodar `dotnet run` de outra pasta: o .NET procura o `.csproj` no diretório atual (ou subpastas).
  Use `dotnet run --project Caminho/Para/MeuApp.csproj`.
- ❌ Editar e não recompilar: **sempre** `dotnet run` ou `dotnet build` para ver as mudanças.
- ❌ Commit de `bin/obj` — nunca versione artefatos de build.
- ❌ Confundir "erro de compilação" com "bug de lógica": o compilador aponta linha/coluna;
  leia a mensagem inteira (o final costuma ter a causa).

## 6. Exercícios

**Fácil — 1.** Crie um projeto `Primeiro`, altere o texto para `Olá, meu nome é X` e rode.
Confirme que `dotnet build` termina com `Build succeeded`.

**Médio — 2.** Crie uma solução `Curso`, adicione dois projetos console nela e rode o primeiro.
Use `dotnet sln list` para conferir.

**Desafiador — 3.** Rode `dotnet publish -c Release` e descubra **onde** o executável é gerado
e **quantos arquivos** há na pasta publicada. Pesquise: o que a pasta `bin/Release/.../publish`
contém de diferente de `bin/Debug/...`?
